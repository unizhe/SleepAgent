# Plan: SleepAgent 产品信息架构与核心页面主线
_Locked via grill — by Codex + user_

## Goal

在上一轮已锁定的产品定位之上，将 SleepAgent 从“目标选择与 Agent 任务启动工作台”重新组织为以居家老年人为第一用户的产品信息架构。产品主入口固定为“今天、趋势、问问 SleepAgent、记录”四个页面，承载晨间解释与对话照护的连续主线；老人、子女、医生三身份模式保持不变。开发／调试工作台只展示四角色 Product Episode 的 Invocation、ToolReceipt、Evidence、决策日志和历史结果，不执行旧 Dynamic 或固定多 Agent Runtime，也不成为老人理解和使用产品的前提。

## Inherited Product Decisions

本轮直接继承上一轮决定，不重新讨论：

1. 居家老年人是第一用户。
2. 老人、子女、医生三身份模式保持不变。
3. 产品主线是“晨间解释 + 个性化对话照护”。
4. 统一照护循环是：`无感观察 → 晨间解释 → 按需深聊 → 老人确认行动 → 轻量跟进 → 后续数据与感受反馈 → 新一轮解释`。
5. 产品只提供健康观察、建议与协同，不替代医疗诊断。

## Approach

1. 将产品一级导航收敛为“今天、趋势、问问 SleepAgent、记录”，不再把 Agent Run、报告生成器、关怀计划、数据管理和历史任务分别暴露为一级入口。
2. 将“今天”设为默认首页，无需老人选择目标、日期或任务类型，直接呈现最新有效晨间结果及当前状态。
3. 将对话设为独立主页面，同时在“今天”和“趋势”保留带当前上下文的快捷提问入口。
4. 将趋势页从日期范围任务改为7天／30天自然切换，以趋势结论为首、图表为证据，不使用不透明的综合睡眠分数。
5. 将历史报告、每晚摘要、设备质量、照护历史和必要技术详情统一归入“记录”。
6. 将关怀计划作为跨页面业务对象：今天展示当前行动，对话负责确认与调整，趋势观察变化，记录保存历史。
7. 为首页定义完成、处理中、数据不足、无昨夜记录、设备异常和急症六类内容状态；任何状态都不把老人送回任务启动器。
8. 将开发／调试工作台收口为 `ProductEpisodeDiagnosticsWorkspace`，只观察四角色 Product Episode；不保留 `DynamicRadarWorkspace` 的旧 Runtime 执行能力。
9. 优先复用现有页面能力和内容组件，只改变信息归属、默认入口和页面间流转；不在本轮设计新的 Agent 或分析链。
10. 用任务归类测试和四条端到端路径验证信息架构；只有用户无需理解技术概念也能找到入口，才进入下一主题。

## Core Page Mainlines

### 1. 今天

默认首页按照固定优先级展示：

1. **昨夜结论**：一句话说明整体情况，并同步显示数据是否可靠和结果日期。
2. **为什么**：只展示最重要的1–2个依据；更多指标按需展开。
3. **今天怎么做**：只给一个主要建议；正常时允许明确说“继续保持”或“今天无需特别处理”。
4. **继续问我**：首页直接提供输入入口和少量基于当前结果的快捷问题。
5. **正在跟进**：老人已经确认行动时，展示当前唯一主要行动、进度和当天是否需要反馈。
6. **近期变化**：只展示7天／30天最重要的一条变化，点击进入趋势页。

实时心率、呼吸、设备在线状态、任务进度与决策日志不占据首屏，统一进入“记录”或开发工作台。

#### 首页状态

| 状态 | 首页主内容 | 老人下一步 |
| --- | --- | --- |
| 分析完成 | 结论、原因、建议、追问 | 阅读、提问或确认行动 |
| 正在整理 | “昨夜记录正在整理”与明确更新时间预期 | 可询问历史趋势，无需启动任务 |
| 数据不足 | 明确说明无法可靠判断及缺失原因 | 只给一个检查设备或补充感受的动作 |
| 无昨夜记录 | 展示最近一次有效记录的明确日期 | 查看记录或设备状态，旧结果不冒充昨夜 |
| 设备异常 | 易懂的设备问题和是否需要处理 | 进入“记录—设备与数据质量” |
| 急症边界 | 覆盖普通晨间内容的强安全提示 | 优先寻求线下医疗或急救协助 |

### 2. 趋势

默认结构：

1. **趋势结论**：先回答最近整体变好、稳定、变差或数据不足。
2. **7天／30天切换**：不要求老人选择精确起止日期。
3. **关键变化**：围绕睡眠时长、连续性／离床、作息规律、呼吸与心率稳定性，只突出真正变化的项目。
4. **为什么这样判断**：展示简单趋势图、实际日期范围、有效数据天数和个人历史基准。
5. **可能相关因素**：关联老人已提供的作息、白天困倦、咖啡因或用药变化，不下未经证实的因果结论。
6. **问问这个变化**：带着当前趋势上下文进入连续对话。
7. **照护效果**：存在已确认行动时，展示行动前后变化与主观感受，不声称确定因果。

趋势页不使用单一综合睡眠分数，避免用不透明数字替代证据和不确定性。

#### 趋势页状态

- **数据足够**：展示结论、关键变化、覆盖范围与简单图表。
- **仅够7天**：默认展示7天；30天入口明确标注“数据尚不足”，不生成伪月度趋势。
- **数据不足**：先说明已记录天数和缺失原因，不展示误导性趋势线；仍可进入对话补充主观感受。
- **没有历史**：解释需要积累若干晚记录，并引导返回“今天”或查看设备状态，不显示空白图表。

### 3. 问问 SleepAgent

对话以老人本人和连续历史为中心，不再绑定单个任务或单份报告：

1. 打开后保留近期对话、当前关注问题和正在跟进的行动。
2. 自动理解老人是在问昨夜、近7天、近30天或一般改善建议，不要求填写日期、报告ID或目标类型。
3. 从“今天”或“趋势”进入时自动携带当前页面上下文。
4. 对话顶部持续显示当前依据范围，例如“正在结合昨夜记录”或“正在结合近30天趋势”，老人可以一键切回一般对话；上下文变化时必须明确提示。
5. 回答优先展示易懂解释与一个下一步；个人数据、老人自述、一般知识和未知信息放在“为什么这样说”中分层呈现。
6. 信息不足时在对话中追问少量关键问题；老人确认后才创建轻量跟进行动。
7. 老人可在对话中调整、暂停或结束当前行动；对话页是行动管理的唯一正式入口，首页只展示状态和跳转按钮。
8. Agent过程、工具调用与 Evidence Ledger 只作为可展开依据或开发工作台内容。

#### 对话页状态

- **有连续历史**：显示近期对话、当前上下文和当前行动。
- **首次对话**：用“昨晚怎么样、这个月怎么样、最近睡不好怎么办”等自然问题帮助开始，不展示空白聊天框。
- **个人数据不足**：允许一般性解释，但必须明确哪些内容不是基于本人数据，并主动询问必要感受。
- **暂时无法回答**：保留已存在的晨间与趋势事实，明确说明对话暂不可用；不伪造回答、不把老人送去创建任务。

### 4. 记录

记录页是低频查阅中心，内部固定为四个二级分组，默认进入“睡眠记录”，避免所有历史内容混成一个长页面：

1. **睡眠记录（默认）**：睡眠日历，以及某晚的结论、关键依据、建议和数据质量。
2. **我的报告**：保存现有老人、家属、医生三类报告材料。
3. **照护记录**：查看已结束、取消或调整过的行动与反馈。
4. **设备与数据质量**：查看离线、缺失、覆盖不足和实时设备信息。

老人可在每晚摘要中查看易懂的“数据来源与更新时间”，但不直接看到任务ID、Agent调用或 Evidence Ledger。开发／调试工作台的跳转只在获授权的内部环境或开发身份下出现，不属于老人记录页的默认信息层级。

#### 记录页状态

- **有记录**：默认显示睡眠日历及最近有效夜晚。
- **暂无记录**：说明尚未形成睡眠记录，并显示设备是否正常采集；不展示空报告或虚构历史。
- **部分内容为空**：每个二级分组独立说明“尚无报告／照护记录／设备事件”，不影响其他分组使用。

“历史任务”不再作为面向老人的页面名称；任务只是记录背后的技术对象。

## Cross-Page Care Object

现有“关怀计划”不再作为第五个一级页面：

| 页面 | 当前行动的职责 |
| --- | --- |
| 今天 | 展示当前唯一主要行动和今天是否需要反馈；管理操作跳转对话页 |
| 问问 SleepAgent | 作为唯一正式管理入口，解释、确认、调整、暂停或停止行动 |
| 趋势 | 展示行动期间的客观变化与老人感受 |
| 记录 | 保存历史行动、反馈和结束原因 |
| 通知 | 仅提示晨间摘要已生成、需要一次反馈或必须处理的异常 |

跨页面只使用五个行动状态：`待确认、进行中、已暂停、已完成、已结束`。其中“停止”操作落为“已结束”并保留原因；四个页面使用相同名称，不各自创造“已启用、观察中、执行中”等同义状态。

## Core User Paths

1. **晨间照护路径**：打开“今天” → 看懂昨夜 → 继续追问 → 确认一个行动 → 后续首页跟进。
2. **长期趋势路径**：进入“趋势” → 查看7天／30天变化 → 追问原因 → 进入连续对话。
3. **数据问题路径**：首页说明数据不足或设备异常 → 进入“记录”查看原因与一个处理动作。
4. **协同升级路径**：持续异常 → 老人得到明确建议 → 沿用现有三身份模式生成家属或医生材料。

## Existing Capability Reuse

本轮不是重新造页面能力，而是重组现有资产：

| 现有能力／组件 | 新归属 |
| --- | --- |
| `TodayAnalysis`、`ElderView`、晨间角色报告 | “今天”的结论、原因、建议内容基础 |
| `TrendFollowup`、现有7天趋势和雷达趋势摘要 | “趋势”的图表与解释基础 |
| `ChatAgentPage`、`ChatPanel`、现有角色问答 | 连续对话页与跨页面快捷提问基础 |
| `ReportCenter`、角色报告 Artifact | “记录—我的报告” |
| `AlertSettings`、关怀候选与确认 | 跨页面当前行动和通知设置 |
| `DataManagement`、质量摘要、设备实时状态 | “记录—设备与数据质量” |
| Product Episode、任务历史、决策日志 | 独立开发／调试工作台 |
| 旧 `AgentRunPage`、Agent 时间线与工具卡 | 只复用展示模式；不得保留旧 Runtime 执行入口 |

复用分为两类，必须明确区分：

1. **可复用产品能力**：当前 radar 任务结果、角色报告、数据质量、趋势摘要、确认状态和审计能力继续作为真实事实来源。
2. **只复用交互模式**：`TodayAnalysis`、`TrendFollowup`、`ChatAgentPage`、`ReportCenter` 等旧组件中的卡片结构、图表交互、对话布局和报告操作可以借鉴，但其中的 SHHS／PSG、AHI、固定日期、mock 病人、单任务上下文和旧字段不能进入新的 radar-first 产品内容。

`LegacyFixedRadarWorkspace` 与 `DynamicRadarWorkspace` 只能作为迁移期交互参考，不能作为产品或开发 Runtime 重新启用。诊断工作台必须读取四角色 Product Episode 的真实记录，任何复用都必须服从新的页面层级、封闭 roster 和当前真实数据边界。

## Preserved Role Boundary

本计划定义老人第一用户的产品主入口，不重新设计子女和医生模式：

1. 现有老人、子女、医生身份与其原有授权边界保持不变。
2. “记录—我的报告”只展示当前身份本来有权查看的材料；页面重组不自动授予老人、家属或医生新的跨身份访问权。
3. 持续异常时仍沿用现有模式生成家属或医生材料，并保留确认要求。
4. 后续若单独讨论家属或医生信息架构，应作为新的主题，不反向改变本轮老人主入口。

## Information Architecture Acceptance Criteria

1. 老人进入产品后默认到“今天”，不需要创建任务或选择日期。
2. 一级导航只有“今天、趋势、问问 SleepAgent、记录”四项。
3. 老人能在首页首屏找到昨夜结论、原因、建议和提问入口。
4. 从首页和趋势页进入对话时无需重复描述当前夜晚或趋势上下文。
5. 对话不要求报告ID、任务ID、目标类型或手动日期范围。
6. 老人能用一次导航找到近30天趋势、历史某晚、报告、设备问题和当前照护行动。
7. 数据不足、无记录和处理中状态不会展示虚假昨夜结论，也不会要求老人启动技术任务。
8. 正常夜晚不会为了填充页面而制造风险、建议或行动。
9. Agent运行、Evidence Ledger、任务ID和决策日志不会出现在默认老人页面；只有获授权的内部环境或开发身份可进入完整工作台。
10. 现有老人、子女、医生三身份材料仍可找到，事实不因页面重组而改变。
11. 急症边界在四个产品页面中都能覆盖普通内容并提供明确行动。
12. 当前行动在四页中状态一致，不会出现首页进行中、对话已停止、记录仍显示进行中的冲突。
13. 趋势、对话和记录在数据不足、首次使用或暂不可用时都有明确下一步，不出现空白页、伪造内容或技术任务入口。
14. 页面重组不扩大任何身份的报告访问权，未授权材料不会因为被归入“记录”而可见。
15. 新产品页不显示 SHHS／PSG、AHI、固定病人或 mock 单任务内容，除非它们确实来自当前获授权的补充材料并被明确标识。

## Manual IA Test

本轮只做简单的“去哪里找”测试，不要求当前代码已经实现新页面。请测试者只看页面树，然后回答以下任务应该进入哪个一级入口：

1. 看昨晚睡得怎么样。
2. 问为什么昨晚总醒。
3. 看这个月整体有没有变差。
4. 继续执行或停止一个改善行动。
5. 找上个月某一天的睡眠结果。
6. 查看给医生的材料。
7. 查为什么设备昨晚没有数据。
8. 查看 Agent 为什么做出某个判断。
9. 只有3晚数据时查看“这个月的趋势”。
10. Chat暂时不可用时查看昨夜事实。

预期答案依次为：今天；今天快捷提问或问问 SleepAgent；趋势；问问 SleepAgent；记录；记录；记录；开发／调试工作台；趋势页说明数据不足；今天仍可阅读已有晨间事实，对话页明确暂不可用。

通过条件：测试者无需理解任务、Artifact、Evidence Ledger 或 Agent Run，即可在10秒内为前7项选择正确入口；第8项能够明确识别为内部开发能力，不会在老人产品导航中寻找；第9、10项不会通过虚构数据或要求创建任务来解除空状态。

## Key decisions & tradeoffs

- 四入口结构牺牲了所有功能都在导航中直接可见的完整感，换取老人更低的选择负担。
- Chat 同时是独立主页面和跨页面入口，接受一定入口重复，换取对话作为产品主力点的可达性。
- 趋势使用结论优先、图表辅助且不设综合分数，牺牲单数字传播性，换取透明度与可信度。
- 报告、设备、质量和技术记录合并到“记录”，减少导航数量，但要求记录页内部层级清晰。
- 关怀计划跨页面分布而非独立存在，换取完整照护循环，但必须保持单一状态源和文案一致。
- Product Episode 诊断工作台只保留可观测性，不保留旧 Dynamic Runtime，避免调试面成为备用架构。
- 技术详情仍可访问，但采用渐进披露，不让专业可追溯性支配老人默认体验。

## Risks / open questions

- “记录”虽然已固定为睡眠记录、我的报告、照护记录、设备与数据质量四个二级分组，但若后续把任务或开发日志再次塞入默认分组，仍会退化成杂物页。
- Chat 横跨首页、趋势和独立页面，若上下文切换不透明，老人可能不知道系统依据的是昨夜还是近30天。
- 当前行动跨四页出现，若状态与措辞不一致，会损害信任。
- 自动晨间入口必须严格区分最新有效结果、处理中状态和旧记录，避免把旧结果冒充昨夜。
- 当前产品前端默认以家庭身份和任务为中心；本轮信息架构虽已明确目标，但真实身份入口与数据准备能力仍需后续主题处理。
- 现有旧组件混合 radar、PSG 和 mock 语义；后续若只按视觉相似度复用，可能把已经退出主线的研究内容重新带回产品。
- 本轮未决定具体导航形态、视觉密度、字号、图表样式和语音交互，留待后续体验设计主题。

## Out of scope

- 重新讨论产品定位、第一用户或老人／子女／医生三身份模式。
- 具体视觉风格、配色、字号、图标、动效和响应式布局细节。
- Agent 数量、Agent 分工、A2A、LangGraph、Prompt 或模型选择。
- API、数据库、缓存、任务调度和自动分析触发的技术实现。
- 雷达供应商接入、设备协议和真实数据质量验证。
- 商业模式、定价、渠道和合规认证。
- 本轮直接修改前端或后端代码。
