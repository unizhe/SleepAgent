# SleepAgent Codebase Curator

## 目标与裁决顺序

将 SleepAgent 整理为职责明确、入口清晰、注释可读、模块边界稳定的 Python 工程。

按以下优先级裁决冲突：

1. 用户明确要求和本 Skill 的不变量。
2. SleepAgent 当前真实调用链、公共合同、测试和部署配置。
3. [qiqihezh/deepresearch-agent](https://github.com/qiqihezh/deepresearch-agent) 的可读性手法。

只借鉴参考仓库的边界说明、显式公共面、职责分区和“解释为什么”的注释。不要复制其业务架构、目录名称、模块编号、状态机、Schema 名称、Tool 名称或 runner 形态；不要照搬脚本中的日志包装、`sys.path` 注入和业务逻辑。

## 确认仓库、模式和范围

1. 找到包含 SleepAgent `pyproject.toml` 的真实 Git 根目录。遇到嵌套或同级 Git 仓库时，分别标记，禁止跨仓库修改。
2. 读取仓库级 `AGENTS.md`、`README`、`pyproject.toml`、CI、Docker/Compose、入口配置和目标模块文档。
3. 记录 `git status --short`，区分：
   - 当前存在的 tracked 文件；
   - tracked 但已删除的旧文件；
   - untracked 新实现；
   - ignored 的缓存、构建、运行或参考产物。
4. 不要把 Git `HEAD`、文件名或目录名单独当作权威证据。结合打包配置、部署入口、当前 import、测试和明确的架构声明确定权威实现。
5. 确认模式只能是 `audit`、`refactor` 或 `document`。
6. `refactor` 和 `document` 必须有一个用户指定模块。把“模块”解释为一个内聚包或一条有边界的应用能力，不要解释为整个仓库。
7. 用户未指定模块时，只做足以列出候选模块的只读分析，然后请求用户选择；不要自行启动全仓重构。
8. 发现目标文件已有用户改动时，展示重叠范围。能明确保留时只追加本轮增量；无法安全区分时停止修改并请求方向。

禁止覆盖、清理或回滚既有改动。禁止使用 `git reset --hard`、宽泛的 `git checkout`、`git clean` 或整目录替换。

在写入前建立本轮变更基线：

- 列出唯一允许修改的路径；
- 记录每条路径的存在性、tracked/untracked 状态、内容哈希和已有 diff；
- 把后续变更维护为仅属于本轮的增量 patch；
- 对不在允许列表中的状态变化视为范围泄漏并立即停止。

需要保存 pre-image 时，只放入仓库外的任务专用临时目录，不要复制密钥或用户数据。结束后只清理本轮创建且路径已核实的临时目录。

## 冻结行为合同

在 `refactor` 和 `document` 中，把下列内容视为不可改变：

- 公共模块路径、包级 re-export、`__all__`、公共符号名称、函数和方法签名；
- 返回类型、错误类型、HTTP 路由、状态码、CLI 参数、退出码和 ASGI `module:app`；
- Pydantic/dataclass/TypedDict/JSON Schema 的字段、类型、别名、默认值、约束、枚举值和版本；
- 配置键、环境变量、默认值、优先级、解析规则及 fail-open/fail-closed 行为；
- 事件名称、载荷、顺序、重试、幂等键、关联标识和投递语义；
- 数据库表、迁移顺序、约束、事务边界、冲突策略、查询结果和持久化/保留语义；
- 进程启动与关闭顺序、后台 worker、日志/指标、网络、缓存和文件系统副作用；
- 前端 BFF 路径、跨语言序列化合同及 package-data。

若完成整理必须改变其中任何一项，停止本轮，把它报告为独立设计变更，不要把合同变化伪装成重构。

## 建立仓库地图

在所有模式中先做静态取证；按需使用 `git ls-files`、`rg --files`、`rg`、`wc`、Python AST 或仓库已有分析工具。

### 分类文件

至少识别并说明证据：

- **生产代码**：打包、部署或运行入口可达的 Python 包、应用入口、配置、迁移和 package-data。
- **设计文档**：ADR、方案、领域模型、设计主题目录和研究材料；不要把它们混入生产 Python 包。
- **测试**：单元、集成、合同、回归、端到端和验收测试。
- **评测**：benchmark、evaluation、数据集、指标和分析脚本；不要与生产测试混为一类。
- **运行产物**：日志、数据库、缓存、构建目录、证据包、报告、模型输出和压缩包。
- **外部参考**：嵌套仓库、vendor、论文解析材料、参考客户端或样例。先核对打包配置，避免把已发布的客户端误判为外部样例。

### 识别结构风险

- 从用户可见入口向内追踪到目标模块，再追踪目标模块的调用方、依赖、Adapter、Memory、事件和持久化。
- 同时检查静态 import、延迟 import、插件注册、字符串入口、反射、配置驱动加载和包级 re-export。
- 结合 AST/字段签名、序列化结果、调用方、测试和版本标识判断重复实现；不要只按同名类或相似文件名合并。
- 把处理同一用例、但由 `legacy`、`new`、`v2`、兼容路径或不同入口选择的实现标为“平行实现候选”，再查明运行时权威。
- 把 Python 文件超过约 500 行、顶层定义过多、同时承担多个变化原因或包含多个层级职责的文件列为超大文件候选。行数只是信号，不是自动拆分理由。
- 建立跨层依赖图，重点查找生产代码依赖 scripts/测试/评测、领域层依赖具体 Adapter、应用层绕过合同直连存储、双向包依赖和复制 Schema。

为每个候选记录：路径、当前职责、运行时证据、调用方、依赖、合同、权威状态、风险和建议归属。

## `audit` 模式

严格只读。禁止新增、修改、移动、删除任何文件，也不要生成缓存、数据库、报告文件或临时补丁。

1. 在开始和结束时使用禁用 optional locks 的 Git 状态命令检查 tracked、untracked 和 ignored 项，确认没有由本轮产生的变化。
2. 只运行静态、只读命令。不要运行可能写入 `__pycache__`、测试缓存、数据库、快照、日志或生成物的 import、测试、`compileall`、格式化、代码生成和应用启动命令。
3. 输出：
   - 仓库分类清单及权威判定依据；
   - 所有运行入口和主要调用链；
   - 重复实现与平行实现候选，明确“已证实”或“待验证”；
   - 超大文件及其混合职责；
   - 跨层依赖和循环依赖；
   - 按风险与收益排序的问题；
   - 建议的下一批单模块 `refactor` 或 `document`，但不要实施。
4. 在结尾明确写出“修改文件：无”，并报告工作树前后是否一致。

## `refactor` 模式

每轮只整理一个用户指定模块。允许触碰目标模块、它的定向测试、必要直接调用点中的机械 import/re-export，以及维持原入口所需的 composition root 装配；不要顺带修改相邻模块的业务逻辑。

1. 先运行可用的定向基线测试，记录已有失败。
   - 缺少回归保护时，先把最小 characterization/合同测试列入实施前映射，再在结构调整前补上并运行。
   - 缺少安全冒烟入口时，把从现有公共入口触达目标模块的最小隔离 smoke 测试列入映射。
2. 确认唯一权威实现和最终归属。权威不明时不要合并或移动。
3. 按变化原因拆分大文件，把纯计算、合同、应用编排、基础设施接入和进程装配分开；不要仅为降低行数拆文件。
4. 移动实现时更新内部 import。若旧公共 import 路径必须保留，只留下无业务逻辑的 re-export/委托兼容层，并保证生产逻辑只有一个权威实现。
5. 合并重复实现前证明字段、默认值、异常、副作用、序列化、事件和持久化语义等价。仅“看起来相似”时不要合并。
6. 把 CLI/scripts 限制为参数解析、输入转换、调用应用层入口和退出码转换。把配置加载、依赖装配、worker 生命周期和系统初始化集中到当前权威 bootstrap/composition root。
7. 把跨模块合同放到已有的明确所有者中；不要为了“统一”建立第二套 contracts 包。若集中合同会扩大到另一个模块，把它拆为后续轮次。
8. 保持现有架构演进方向。不要新建并行 package、旁路入口或第二套 service graph。
9. 不要为了形式引入无意义的 `Base`、`Manager`、`Factory`、`Wrapper`、注册表或抽象层。只有存在两个真实实现或明确替换边界时才考虑抽象。
10. 避免与目标无关的重命名、格式化和 import 重排，使 diff 能证明行为等价。

## `document` 模式

只为一个用户指定模块补充可读性文档和注释；不要借机移动、重命名或重写逻辑。

### 文件头

为人工维护的生产模块添加简洁模块 docstring，说明：

- 负责什么；
- 明确不负责什么；
- 主要输入和输出；
- 稳定公共接口；
- 复杂模块才需要补充关键不变量或设计理由。

不要保留没有内容的空模板字段。不要强制添加 shebang、编码声明、装饰性横幅或外部仓库的模块编号。

### 公共类和方法

- 公共类说明它在调用链中的角色、关键协作者/依赖，以及有意义的生命周期或运行状态。
- 公共方法使用项目既有 docstring 风格；没有约定时使用简洁的 Google 风格。
- 准确记录参数、返回值、实际可能抛出的异常和关键副作用，包括网络、持久化、事件、缓存、日志及资源生命周期。
- 让类型标注承担可直接表达的类型信息，不要在 docstring 中机械重复。
- 私有函数只有在算法、协议、降级路径或不变量不明显时才补充 docstring。
- 添加运行时可见 docstring 前检查 FastAPI/OpenAPI、CLI help、插件发现、反射或快照是否消费 `__doc__`；可能改变公共元数据时改用普通注释或补充合同测试。

### 分区和行内注释

- 只在确有一级职责边界时使用分区注释，例如“公共 API”“内部实现/私有方法”“辅助函数”，按需增加“合同/常量”。
- 不要为一两个简单函数增加装饰性分区。
- 复杂逻辑解释设计原因、不变量、权衡、降级策略、防御条件和异常选择。
- 只在编号代表协议或算法阶段时使用步骤注释。
- 删除或不新增复述赋值、循环、条件、函数名和返回语句的注释。
- 注释语言遵循目标模块现有约定；没有约定时使用简洁中文并保留准确的代码术语。

## 维持模块边界

保持职责单一且依赖方向明确：

- **Agent**：作出受合同约束的推理或决策，不直接承担基础设施装配。
- **Skill**：描述可发现的能力和执行规约，不复制 Tool 或应用服务实现。
- **Tool**：提供窄而可测试的动作合同，不编排完整业务流程。
- **Adapter**：隔离外部 API、设备、数据库或模型 SDK，不拥有领域决策。
- **Memory**：负责记忆的写入、检索、生命周期和一致性，不承担 Agent 编排。
- **应用编排**：协调用例、事务和组件协作，不实现外部协议细节。
- **bootstrap/composition root**：选择具体实现并管理进程级生命周期，不承载业务规则。
- **跨模块合同**：由一个明确位置权威定义，通过稳定公共面复用，不复制相似 Schema。

设计主题目录只提供约束和证据，不要与生产包混合。目录名称服从 SleepAgent 当前语言，不要为了模仿参考仓库而改名。

## 实施前输出

在 `refactor` 或 `document` 修改任何文件前，先向用户输出以下内容。若没有实质歧义，可在同一轮继续；若权威实现、合同或范围不明确，等待用户确认。

```markdown
模式：refactor | document
目标模块：<唯一模块>

当前调用链：
- <用户/运行入口> → <应用入口> → <编排> → <目标公共 API> → <依赖/Adapter/Memory>
- 调用方：...
- 被调用方：...

保持不变的接口：
- <import/符号/签名>
- <Schema/配置/事件/数据库/入口语义>

修改和移动映射：
| 原路径/符号 | 新路径/符号 | 操作 | 兼容措施 |
| --- | --- | --- | --- |

验证命令：
1. <定向测试>
2. <compileall>
3. <项目已配置的类型检查>
4. <入口或用例冒烟测试>

回滚方式：
- <仅反向应用 agent-only patch 的新增 hunks/移动；不得恢复整文件或覆盖既有改动>
```

`document` 没有移动时，也要在映射中写明“原路径 = 新路径，doc-only”。

## 验证要求

先从 `pyproject.toml`、CI、README、Makefile 或现有脚本发现真实命令，不要编造命令或擅自安装依赖。

在实施前确认四类验证都有明确命令；缺少定向回归或隔离 smoke 时，可把最小测试加入本轮映射。Python 类型检查器未配置或不可用时，把它视为实施阻塞：报告缺失并建议先进行独立的工具链准备轮次，取得用户授权前不要安装、配置或继续当前整理。不要用 `compileall` 代替类型检查，也不要把新增类型检查基础设施偷偷纳入当前模块整理。

实施后必须依次运行：

1. 与目标模块和直接调用点相关的测试；
2. 使用项目解释器执行 `python -m compileall`，只覆盖改动的 Python 包或文件；
3. 项目已配置的 Python 类型检查，至少覆盖改动路径；
4. 从真实入口触达目标模块的最小冒烟测试。

为测试设置 `PYTHONDONTWRITEBYTECODE=1`。`compileall` 会显式写入 `.pyc`，必须把 `PYTHONPYCACHEPREFIX` 指向仓库外、路径已核实的任务专用临时目录。把 pytest、类型检查、coverage、构建工具和应用产生的 cache、temp、日志、数据库及输出也通过各工具现有选项定向到该目录，不要为此改变测试语义。完成后只清理本轮创建且路径已核实的临时目录。冒烟测试使用临时数据库、mock/fake 或本地隔离配置；禁止连接生产系统、写入真实用户数据或调用有成本的外部服务。触及前端或跨语言合同时，额外运行已有的前端 typecheck/build 和合同测试。

再对 agent-only patch 或允许路径运行 whitespace/diff 检查，并把包含 ignored 项的结束状态与逐路径基线比较。不要用整个脏工作树的 `git diff --check` 结果归因于本轮。对每条命令记录实际命令、退出码、关键结果和已有/新增失败；没有运行的检查不得写成通过。

## 实施后输出

按以下顺序交付：

1. **修改文件**：逐文件说明新增、移动、删除或 doc-only。
2. **行为等价依据**：把调用链、兼容层、合同快照和 diff 与冻结项对应起来。
3. **测试结果**：列出定向测试、`compileall`、类型检查、冒烟测试和本轮增量 diff 检查的实际结果。
4. **剩余风险**：包括未覆盖的动态加载、外部依赖、反射、数据迁移和既有失败。
5. **下一批建议**：只推荐一个或少量明确模块，不要继续实施。

若任何强制验证失败，明确写出“本轮未完成验证”，定位原因；不要以部分测试通过宣称整理完成。

## 停止条件

遇到以下任一情况时停止写入，保留只读取证结果并请求用户决策：

- 用户要求一次性重构整个仓库；
- `refactor` 或 `document` 没有唯一目标模块；
- 权威实现或公共合同无法从证据确定；
- 整理必须改变冻结的接口或语义；
- 必须修改另一个业务模块的业务逻辑才能完成；必要的机械 import/re-export 或 composition root 装配仍可纳入明确映射；
- 必需的类型检查不可用，或定向测试/隔离 smoke 无法在本轮范围内安全补齐并执行；
- 目标范围与既有未提交改动无法安全分离；
- 方案会建立平行架构或无意义抽象。

除非用户另行明确要求，不要提交、推送、删除运行产物或修改外部参考仓库。
