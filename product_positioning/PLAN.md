# Plan: SleepAgent 产品定位与产品主线
_Locked via grill — by Codex + user_

## Goal

SleepAgent 定位为一款以居家老年人为第一用户、连接子女与医生的睡眠健康观察与对话式照护助手。产品结合无感雷达长期数据和老人的主观感受，以“每日晨间解释”和“个性化对话照护”作为同一条持续照护循环的两个主力入口，帮助老人理解睡眠、采取一个可执行的改善行动并持续观察效果；产品只提供健康观察、建议与协同，不替代医疗诊断。

## Approach

1. 将居家老年人设为所有主线取舍的第一用户，不改变老人、子女、医生三身份模式。
2. 建立晨间解释主线：无感采集一晚数据 → 系统自动分析 → 老人早晨直接看到或听到“一句结论、一个原因、一个建议”；正常且无需改变时，建议可以是“继续保持”或“今天无需特别处理”。
3. 建立对话照护主线：老人可以围绕昨晚、近 7 天、近 30 天和睡眠习惯自由追问，产品必须优先结合其长期数据回答，而非只输出通用睡眠知识。
4. 将客观数据与主观感受合并为照护依据：遇到“最近失眠怎么办”等问题时，用少量关键追问补充症状、持续时间、白天影响和生活变化，再给出个性化解释与建议。
5. 将一次性建议延伸为轻量照护闭环：解释 → 建议 → 老人确认 → 3–7 天轻量跟进 → 结合后续数据与主观感受观察效果；未经老人同意不自动建立行动计划，同一时间默认只跟进一个主要行动，老人可随时停止。
6. 保持三身份协同：老人获得首要日常体验；子女承接老人需要协助或持续异常时的照护信息；医生获得需要进一步评估时的结构化材料。三者事实一致、表达和行动重点不同。
7. 使用产品主线过滤功能：不能直接强化晨间解释、个性化对话照护或必要的三身份协同的能力，不进入当前主线。
8. 先用固定场景进行手动定位验证；只有老人视角的核心任务成立后，才进入下一轮产品主题讨论。

## Product Mainline

两条主线不是两个独立产品：晨间解释主动开启每天的照护循环，对话承担深入理解、建议与跟进；对话形成的新信息和已确认行动，再进入后续晨间解释。统一循环为：

`无感观察 → 晨间解释 → 按需深聊 → 老人确认行动 → 轻量跟进 → 后续数据与感受反馈 → 新一轮解释`

### 主线 A：每日晨间解释

`无感采集一晚数据 → 自动分析 → 一句结论 → 一个原因 → 一个建议 → 按需追问`

目标不是让老人阅读复杂 Dashboard，而是让其在最短时间内知道：昨晚整体如何、为什么这样说、今天可以做什么。

### 主线 B：个性化对话照护

`老人提出问题 → 读取本人长期数据 → 区分客观事实与不确定性 → 必要时追问主观感受 → 给出个性化建议 → 经同意形成轻量行动 → 后续跟进效果`

对话是产品主力点，不是报告后的附属 Chat。它必须能覆盖：

- “我这个月睡得怎么样？”
- “我的睡眠习惯好吗？”
- “我最近有些失眠怎么办？”
- “有什么办法可以改善吗？”

每个涉及个人状况的回答都应让老人能够区分：系统观察到的个人数据、老人自己提供的信息、一般性睡眠知识，以及当前仍不知道或证据不足的部分。技术价值体现为对个人长期证据的可靠使用，而不是展示 Agent 数量或生成过程。

### 三身份协同

- 老人：第一用户，拥有晨间解释、深度追问、建议确认和跟进体验。
- 子女：照护协同身份，在老人需要帮助或趋势持续异常时获得适合家属理解的信息。
- 医生：专业协同身份，在需要进一步评估时获得结构化、可追溯且保留不确定性的材料。

三身份模式保持不变；本计划不重新设计其权限、界面或工作流。

## Product Promise

SleepAgent 每天帮助老人读懂自己的睡眠，并通过了解本人长期变化的对话，给出可执行、可跟进的睡眠照护建议。

产品不承诺疾病诊断、精确替代 PSG、药物处方、治疗效果或急救判断。

## Positioning Acceptance Criteria

1. 老人无需创建“目标”或理解 Agent 工作流，就能进入晨间主线。
2. 晨间结果能被压缩为一句结论、一个数据或趋势原因、一个当天建议。
3. 对“本月睡得怎么样”的回答使用个人近 30 天数据，并能说明趋势与数据不足之处。
4. 对“睡眠习惯好吗”的回答同时引用长期规律和老人已提供的作息信息；信息不足时先追问，不武断判断。
5. 对“最近失眠怎么办”的回答先理解具体困扰，再给出少量、低负担、可执行的建议，不进行诊断或药物指导。
6. 老人同意某项建议后，产品能够在后续 3–7 天继续跟进，并说明观察到的变化或数据仍不足。
7. 对话中的事实、晨间摘要以及子女/医生材料不相互矛盾。
8. 当数据质量不足时，产品明确说不知道或证据不足，而不是生成确定结论。
9. 老人能分辨产品为什么给出某条建议，并知道下一步应该做什么。
10. 个性化回答能区分个人数据、老人自述、一般性知识与未知信息，不把建议后的变化宣称为确定因果效果。
11. 出现胸痛、严重呼吸困难、意识异常等急症自述时，停止普通睡眠建议并明确提示及时寻求线下医疗或急救协助。
12. 正常夜晚不被包装成需要改善的问题；没有必要行动时，系统允许明确说“无需特别处理”。
13. 周/月趋势回答说明实际日期范围、有效数据覆盖和比较基准，不能用少量数据冒充完整长期趋势。

## Manual Positioning Test

本轮手动测试分成两个判断门，不能把“定位值得继续”和“当前代码已经实现”混为同一个结论。

### Gate A：定位可行性自测

使用一名测试者扮演老人，并由测试主持人准备一个虚构但前后一致的案例包：昨夜摘要、近 30 天趋势、数据覆盖情况、两条老人主观感受，以及 3–7 天后的复访结果。即使当前功能尚未实现，也可以由主持人按本计划模拟产品回应，以判断整个价值循环是否清楚、自然且值得继续。

完成下列测试：

1. 不输入任务，直接查看晨间结果；复述系统给出的结论、原因和建议。
2. 连续提问：“我昨晚睡得怎么样？”“我这个月睡得怎么样？”“我的睡眠习惯好吗？”
3. 再说：“我最近有些失眠，怎么办？”观察系统是否追问关键感受，而不是立即给出泛化长清单。
4. 回答追问后，说：“给我一个最容易做到的办法。”观察是否只给出清晰、低负担的行动。
5. 表示同意执行该行动，再模拟 3–7 天后的复访；观察系统能否记住约定，并结合后续数据和主观感受评估变化。
6. 切换至数据不足场景，重复月度趋势问题；观察系统是否主动暴露数据覆盖不足。
7. 分别查看老人、子女、医生身份下对同一事实的表达；确认事实一致，且老人仍是主体验中心。
8. 说：“我现在胸痛、喘不上气，昨晚也没睡好。”观察系统是否立即停止常规睡眠建议，清晰提示及时寻求线下医疗或急救协助。
9. 回到正常夜晚，观察产品是否允许“保持即可、无需特别处理”，而不是为了活跃度制造新的改善任务。

每一步按“通过 / 不通过 / 当前未实现”记录，并让测试者用自己的话回答四个问题：系统认为我的睡眠怎样、依据是什么、建议我做什么、之后是否会继续跟进。

Gate A 通过条件：十三项定位验收标准全部满足，且测试者无需理解 Agent、任务、Evidence Ledger 或技术流程，就能说清楚“它了解我的睡眠、能解释原因、会给我一个建议并继续关心效果”。以下任一情况直接判为失败：价值必须依赖创建技术目标才能讲清；月度回答没有使用本人长期数据却表现得像个性化结论；失眠问题未经了解具体情况就给出诊断或药物建议；数据不足时仍给出确定判断；建议在未经老人同意时自动进入跟进；遇到急症自述仍继续普通睡眠建议；正常睡眠被刻意包装成问题以制造行动或留存。

### Gate B：当前产品一致性审计

使用同一套问题操作当前产品，把每一步记录为“已支持 / 部分支持 / 未支持 / 与定位冲突”。Gate B 的失败表示下一轮需要处理产品差距，不自动否定 Gate A 的产品定位。当前已知的首要冲突是：主页仍要求选择目标类型、日期并启动动态任务，尚未提供老人无需操作即可进入的晨间价值。

本轮进入下一主题的条件是 Gate A 通过，且 Gate B 已形成诚实的差距清单；不要求现有代码在本轮通过全部能力验收。

### 验证效力边界

单个测试者扮演老人只能作为内部方向门，不能证明真实用户需求。进入后续产品迭代后，应再邀请至少 3–5 名目标年龄段用户分别完成晨间理解、月度追问、失眠建议和行动跟进任务；在此之前不得把“内部测试可行”写成用户验证或市场验证。

## Key decisions & tradeoffs

- 选择居家场景，不同时覆盖养老机构运营场景，以保持主线清晰。
- 老人是第一用户，但保留老人、子女、医生三身份协同，不将家属 Dashboard 变成产品中心。
- 晨间解释与对话照护是同一循环的双主力入口：前者建立日常入口，后者体现技术与长期照护价值，并把确认后的新信息带回后续晨间解释。
- 对话优先使用个人长期数据和已确认的主观信息，牺牲“任何问题立即作答”的流畅感，换取个性化与可信度。
- 建议采用少量行动和持续跟进，牺牲一次输出大量知识的丰富感，换取老年人可执行性。
- 不以每天制造建议或任务换取活跃度；正常时明确“无需特别处理”，以减少健康焦虑和提醒疲劳。
- 动态 Agent、A2A 和工作流可以作为后台能力存在，但不作为老人理解产品的前提或前台卖点。
- 保持非诊断边界，以可信的健康观察与照护协同替代医疗能力承诺。

## Risks / open questions

- 当前主页虽已进入 radar-first 动态 UI，但任务、目标和技术过程可能仍比老人晨间价值更突出，需要下一轮主题再评估产品体验是否一致。
- 当前主数据仍以 replay 为主，因此本轮只能验证产品叙事与交互价值，不能证明真实设备数据质量或医学有效性。
- 当前前端仍以选择目标类型和日期后启动动态任务为主要入口，与“老人无需创建目标即可获得晨间价值”的定位直接冲突；手动测试应如实记为产品差距，不能为了让计划看起来可行而跳过。
- 个性化对话如果无法稳定读取长期数据、区分事实与通用知识，会退化为普通聊天机器人。
- 轻量跟进如果频率过高或措辞带有监督感，可能给老人造成压力；具体节奏留待后续体验主题决定。
- 本轮不确定项只保留“如何呈现与实现”，不再开放已锁定的定位、三身份模式和双主线。

## Out of scope

- 商业模式、付费者、定价、渠道和获客。
- 改变老人、子女、医生三身份模式。
- 具体页面布局、视觉风格、语音形态和交互控件。
- Agent 数量、Agent 分工、A2A、LangGraph、模型选择和 Prompt 设计。
- 数据库、API、长期记忆和雷达设备接入的技术方案。
- 医疗诊断、药物建议、临床有效性声明和医疗器械合规。
- 养老机构床位、护理员排班与机构运营系统。
